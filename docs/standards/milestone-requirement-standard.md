# QuantKYND Milestone Requirement Standard

## Purpose

This standard is designed to reduce post-implementation review corrections by making architectural, temporal, operational, and acceptance requirements explicit before coding begins.

It does not guarantee zero corrections. It aims to move most corrections from post-implementation review into pre-implementation design review.

---

# 1. Milestone Header

## Milestone

- ID:
- Name:
- Parent roadmap item:
- Required starting branch:
- Required starting SHA:
- Target branch:
- Expected implementation scope:
- Explicitly deferred scope:

## Repository baseline verification

Required commands:

```bash
git switch <starting-branch>
git pull --ff-only origin <starting-branch>
git rev-parse HEAD
git status --short
git merge-base --is-ancestor <required-sha> HEAD
```

Required conditions:

- exact expected SHA;
- clean worktree;
- no unrelated local commits;
- no untracked implementation artifacts unless explicitly listed.

---

# 2. Problem Statement

Describe:

- what the milestone enables;
- what existing limitation it removes;
- why the milestone exists now;
- what later milestones depend on it;
- what must remain unchanged.

Avoid describing only the implementation technology.

---

# 3. Architectural Boundary

State the dependency direction explicitly.

Example:

```text
API / CLI
    ↓
Application services
    ↓
Domain models and policies
    ↓
Ports
    ↓
Infrastructure adapters
```

List forbidden dependencies.

Example:

- domain must not import SQLAlchemy;
- application services must not expose `AsyncSession`;
- repositories must not commit independently;
- simulations must not require Postgres;
- infrastructure must not leak provider SDK objects into domain models.

---

# 4. Domain Semantics Freeze

Before implementation, define every important concept.

For each concept provide:

- name;
- purpose;
- fields;
- invariants;
- identity material;
- excluded identity material;
- mutation policy;
- lifecycle;
- error behavior;
- serialization behavior.

Example format:

## `OptionContractIdentity`

### Identity fields

- exchange;
- underlying identity;
- expiry date;
- strike;
- option side;
- exercise style;
- settlement type;
- multiplier;
- currency.

### Explicitly excluded

- provider key;
- display symbol;
- lot size;
- tick size;
- recorded timestamp;
- ingestion timestamp.

### Invariants

- strike is finite and positive;
- multiplier is finite and positive;
- expiry uses exchange date;
- identity is provider-neutral.

---

# 5. State-Transition Model

Every object with lifecycle behavior must include a state-transition section.

Example:

```text
open record
    ↓ later correction becomes known
append successor record
    ↓
prior record remains historically visible
    ↓
successor becomes visible at its recorded_at
```

For every transition specify:

- trigger;
- preconditions;
- new record or mutation;
- identity behavior;
- visibility behavior;
- rollback behavior;
- invalid transitions;
- concurrency behavior.

Do not use words such as “superseded,” “corrected,” “closed,” “latest,” or “current” without specifying how they are represented durably.

---

# 6. Identity Model

For each durable entity, distinguish:

## Semantic identity

The stable meaning of the object.

## Durable record identity

One immutable recorded observation of that semantic object.

## Provider identity

External-system-specific identity.

## Source identity

Source file, row, sequence, event, or ingestion identity.

Requirements must answer:

- Can two records share one semantic identity?
- Is `recorded_at` part of record identity?
- What makes a retry idempotent?
- What makes two identical-looking transmissions distinct?
- What happens when the same ID arrives with different content?
- What values are deterministic?
- What values are generated by the database?
- Can identity change after persistence?

---

# 7. Time Model

Every time-aware milestone must define all clocks.

At minimum distinguish:

- event or exchange time;
- provider receipt time;
- application availability time;
- persistence time;
- knowledge time;
- effective validity time;
- supersession visibility time.

Define:

- inclusive and exclusive interval boundaries;
- timezone requirements;
- UTC storage rules;
- exchange-local interpretation;
- historical import limitations;
- default query semantics;
- current-state semantics;
- absent knowledge-cutoff semantics.

Example:

```text
market validity: [valid_from, valid_until)
knowledge visibility: recorded_at <= known_as_of
supersession: prior record is hidden only when a visible successor references it
```

---

# 8. Persistence Semantics

For each table specify:

- primary key;
- semantic key;
- foreign keys;
- check constraints;
- unique constraints;
- immutable fields;
- append-only fields;
- indexes;
- deletion policy;
- conflict behavior;
- expected point-in-time queries.

Never leave these decisions to the implementation agent.

Include a table-by-table schema sketch.

---

# 9. Transaction Contract

Define:

- transaction owner;
- session lifecycle;
- commit ownership;
- rollback behavior;
- unit-of-work finality;
- nested transaction policy;
- retry policy;
- idempotency boundary;
- concurrency behavior;
- exception translation.

Example:

```text
one unit of work = one database transaction

commit finalizes the unit of work
rollback finalizes the unit of work
repositories cannot be used after finalization
repositories never commit independently
```

---

# 10. Correction and Conflict Rules

Define all failure modes.

At minimum:

- exact duplicate;
- same semantic ID with different content;
- same durable record ID with different content;
- missing supersession target;
- self-supersession;
- cross-entity supersession;
- cycle;
- ambiguous branch;
- overlapping effective intervals;
- overlapping visible provider mappings;
- stale version;
- future record;
- malformed durable row.

For each, say whether the system:

- rejects;
- quarantines;
- appends a correction;
- selects deterministically;
- raises a named exception.

“Fail closed” must name the exact failure.

---

# 11. Security and Destructive Operations

Any command that can:

- drop schemas;
- downgrade migrations;
- delete data;
- restore backups;
- truncate tables;
- reset environments;

must define:

- explicit opt-in;
- exact expected database name;
- host restriction;
- environment restriction;
- disposable-database sentinel;
- advisory lock;
- source-target separation;
- credential redaction;
- audit output;
- refusal behavior.

Substring-based environment or database-name checks are not sufficient.

---

# 12. Operational Environment Prerequisites

List all tools required for acceptance before implementation begins.

Example:

```text
Docker or native PostgreSQL 17
pg_dump
pg_restore
psql
PostgreSQL client/server compatible major versions
```

Separate:

## Development prerequisites

Needed to write code.

## Unit-test prerequisites

Needed for pure tests.

## Integration-test prerequisites

Needed for real infrastructure tests.

## Acceptance prerequisites

Needed to claim the milestone is accepted.

A milestone must not be described as “complete except for acceptance” when the unavailable environment is itself a required milestone deliverable unless that limitation was approved before implementation.

---

# 13. Adversarial Scenario Matrix

Every requirement document must include concrete hostile cases.

Example:

| Scenario | Required behavior |
|---|---|
| Same provider sequence on two feed sessions | IDs differ |
| Correction points to another contract | Reject |
| Two corrections supersede one record | Reject ambiguous branch |
| Record becomes known tomorrow | Invisible today |
| Catalogue B recorded later but effective next week | A remains active until B is effective |
| Same semantic ID, different durable content | Explicit collision |
| Zero bid | Preserve observation; quality policy decides eligibility |
| DB name contains `test` but is not exact expected DB | Refuse destructive operation |
| Commit called twice | Raise UoW state error |
| Restore target equals source through alias | Refuse |

This matrix should directly become tests.

---

# 14. Proof Obligations

State what must be proven, not merely implemented.

Examples:

- input ordering does not alter results;
- exact reinsertion is idempotent;
- later knowledge does not leak backward;
- historical state remains reproducible;
- migration downgrade restores the prior schema;
- backup restoration reproduces row digests;
- secrets never appear in logs;
- offline simulation remains database-independent;
- destructive commands refuse unsafe targets.

---

# 15. Required Tests

Separate tests into:

## Pure unit tests

No external infrastructure.

## Mapping tests

Domain-to-row and row-to-domain.

## Integration tests

Real Postgres or other required infrastructure.

## Migration tests

Upgrade, downgrade, re-upgrade, drift.

## Failure-path tests

Invalid states and exceptions.

## Security tests

Redaction and destructive-operation refusal.

## Determinism tests

Permutation, repeated run, canonical hashes.

## Restore tests

Revision, row counts, canonical digest, representative queries.

Each test group must state whether skipping is allowed.

Acceptance-critical integration tests must require zero skips.

---

# 16. Acceptance Commands

List exact commands and expected outputs.

Example:

```bash
UV_CACHE_DIR=/tmp/uv-cache uv run pytest
UV_CACHE_DIR=/tmp/uv-cache uv run alembic upgrade head
UV_CACHE_DIR=/tmp/uv-cache uv run alembic current
UV_CACHE_DIR=/tmp/uv-cache uv run alembic check
UV_CACHE_DIR=/tmp/uv-cache uv run python -m app.cli.verify_database_restore
npm run lint
npm run build
git diff --check
git status --short
```

State:

- required environment variables;
- expected database names;
- whether skipped tests are allowed;
- minimum evidence required;
- artifact cleanup requirements.

---

# 17. Non-Goals

List forbidden expansion explicitly.

Example:

- no live provider integration;
- no quote persistence;
- no Redis;
- no IV surface;
- no strategy changes;
- no paper orders;
- no broker path;
- no frontend work.

Non-goals must also be checked during review.

---

# 18. Pre-Implementation Design Gate

Before implementation begins, require a short design response containing:

- proposed package layout;
- proposed domain models;
- identity design;
- time model;
- schema;
- transaction model;
- migration sequence;
- failure modes;
- acceptance environment;
- unresolved questions.

No code should be written until the design response is reviewed and approved.

This is the most important step for reducing post-implementation corrections.

---

# 19. Mid-Milestone Checkpoint

For milestones involving persistence, concurrency, execution, or temporal semantics, require a checkpoint after:

- domain contracts;
- schema design;
- first migration;
- repository interfaces;

but before:

- all adapters;
- all tests;
- documentation completion.

The checkpoint should review structure while changes are still inexpensive.

---

# 20. Acceptance Evidence

The evidence document must record:

- starting SHA;
- implementation SHA;
- final evidence SHA;
- commits;
- files changed;
- architecture summary;
- identity model;
- state transitions;
- schema;
- migration revisions;
- exact commands;
- exact results;
- skipped tests;
- tool versions;
- environment limitations;
- security scans;
- known limitations;
- explicit non-goals preserved.

No acceptance claim is permitted while acceptance-critical tests are skipped.

---

# 21. Review Severity Standard

Use:

## Blocker

Can corrupt state, leak future information, execute unsafe actions, or invalidate research.

## High

Breaks core correctness or architecture under realistic conditions.

## Medium

Creates ambiguity, lifecycle weakness, or operational inconsistency.

## Low

Maintainability, clarity, or non-critical coverage improvement.

The requirement document should proactively cover all anticipated blocker and high-severity cases.

---

# 22. Recommended Workflow

```text
requirements draft
    ↓
adversarial review
    ↓
design response
    ↓
design approval
    ↓
implementation checkpoint
    ↓
implementation completion
    ↓
acceptance environment verification
    ↓
final review
    ↓
merge
```

This replaces:

```text
broad requirement
    ↓
full implementation
    ↓
late discovery of lifecycle and failure cases
    ↓
correction cycle
```

---

# 23. Definition of Ready

A milestone is ready for implementation only when:

- domain terminology is frozen;
- identity and time semantics are explicit;
- lifecycle transitions are defined;
- schema shape is specified;
- transaction ownership is specified;
- adversarial cases are listed;
- acceptance environment is available or explicitly scheduled;
- acceptance commands are known;
- non-goals are explicit;
- no unresolved blocker-level question remains.

---

# 24. Definition of Done

A milestone is done only when:

- implementation matches the approved design;
- all proof obligations pass;
- acceptance-critical tests have zero skips;
- migrations and restore verification pass;
- evidence is complete;
- worktree is clean;
- no deferred path was introduced;
- final review finds no blocker or high-severity issue.
